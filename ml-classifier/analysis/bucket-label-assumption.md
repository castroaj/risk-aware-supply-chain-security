# The Bucket-Label Assumption Was the Flaw

After v2 LLM labels were generated and model v0.0.6 was trained, the final label distribution across 371 images was: **ALLOW=21 (6%), WARN=100 (27%), BLOCK=250 (67%)**.

The expectation going in was ~50–65% ALLOW for the high-qual bucket. The initial reaction was to treat the shortfall as a prompt calibration problem. That was the wrong interpretation.

---

## The Circular Reference

The expected distribution targets were derived from threshold-based labels. But those threshold labels were generated by a rule engine (`BLOCK_THRESHOLDS`, `WARN_THRESHOLDS`) that was *calibrated to reproduce bucket identity*: high-qual → ALLOW, aged-stale → WARN, known-vuln → BLOCK.

The loop:

1. Threshold constants were tuned to make high-qual images land in ALLOW
2. Expected distribution targets were set by treating those labels as ground truth
3. The LLM was judged as "miscalibrated" for not reproducing them

At no point was the underlying question asked: **do the feature values of high-qual images actually justify ALLOW by a strict security standard?**

---

## What the Data Actually Says

The median high-qual image has:

| Feature | Median |
|---|---|
| `critical_cve_count` | 3.0 |
| `max_cvss` | 10.0 |
| `cvss_ge_7_count` | 18.5 |
| `vuln_total` | 51.0 |

The v2 BLOCK criterion `critical_cve_count ≥ 2 AND max_cvss = 10.0` fires on more than half of high-qual by definition. A 50–65% ALLOW rate was never achievable from these feature values without lowering the security bar — not without fixing the prompt.

---

## "High Quality" Does Not Mean "Secure"

The three buckets were assembled using operational proxies for risk:

- **high-qual** — recently pushed, popular, well-maintained images → assumed safe
- **aged-stale** — older images with outdated base layers → assumed to have accumulated debt
- **known-vuln** — intentionally vulnerable images (CTF, demo apps) → assumed BLOCK

These proxies measure *maintenance posture*, not *security posture*. A popular, actively-maintained image is typically a large image with a deep transitive dependency tree. Popularity means vulnerabilities get patched *eventually* — not that the image is clean at any given moment. Patching lags behind disclosure.

**Most production container images — even well-maintained ones — do not meet a strict security analyst's threshold for unconditional deployment approval.** This is not a failure of maintainers; it reflects the nature of the modern software supply chain.

The LLM evaluated raw feature values without knowing which bucket an image came from. When it saw `critical_cve_count=3, max_cvss=10.0`, it labeled WARN or BLOCK. That was the correct answer.

---

## What ALLOW=6% Actually Means

The 21 ALLOW images represent the ones that genuinely earned it: no critical CVEs, low high-severity counts, max CVSS below 9.0. Typically minimal base images — Alpine, distroless, scratch-based — or tightly scoped single-purpose images with few dependencies.

ALLOW should be rare and should mean something. A classifier that outputs ALLOW 39% of the time (v0.0.4, trained on threshold labels) was approving images with critical CVEs because the rule engine was calibrated to bucket identity, not feature values.

---

## Implications

**WARN is the correct normal outcome.** For most production images, WARN — deploy with a documented sprint-cycle fix window — is the operationally appropriate response. A gate that ALLOWs 6%, WARNs 27%, and BLOCKs 67% is functioning as a strict security gate. One that ALLOWs 39% is a rubber stamp.

**Buckets are valid for data sourcing, not for label expectations.** The high-qual/aged-stale/known-vuln split is a useful heuristic for collecting a dataset that spans the risk spectrum. It was never a valid prior on what fraction of each bucket should receive a given label. Future dataset expansions should source images from all three buckets without any expected label distribution.

**Calibration means feature-value consistency, not bucket-distribution matching.** The correct check for a future prompt version is whether the LLM's justifications are logically consistent with the feature values in each labeled row — not whether the distribution aligns with bucket identity.

**The v2 BLOCK anchors carry a residual density problem.** Criteria like `critical_cve_count ≥ 2 AND max_cvss = 10.0` do not encode image size, so a 400-dependency image with 2 isolated critical CVEs fires identically to a 5-dependency image with the same profile — very different risk densities, same outcome. A future v3 prompt should make density structural by passing `critical_cve_count / total_dependency_count` as an explicit value in the user message, with thresholds anchored on that rate rather than on raw counts.
